# Roomly — план реализации первого релиза

Статус: в реализации; этапы 1–2 завершены. Нормативный источник: `docs/requirements.md`, версия 1.1.

## Как пользоваться планом

- Задачи выполняются сверху вниз, если внутри этапа не указано иное.
- Чекбокс отмечается только после реализации и проверки результата.
- В конце каждого этапа должны проходить относящиеся к нему проверки.
- При расхождении плана и `requirements.md` приоритет имеет `requirements.md`; план затем актуализируется.
- Новые функции вне первого релиза не добавляются без отдельного изменения требований.
- Коммиты, push и релизные теги выполняются отдельными явными действиями пользователя.

## Зафиксированные технические решения

- [x] Использовать Node.js 24 LTS и зафиксировать версию в `.nvmrc` и `engines`.
- [x] Использовать TypeScript в strict-режиме во всех workspace.
- [x] Организовать monorepo через npm workspaces.
- [x] Реализовать frontend как React SPA на Vite.
- [x] Использовать React Router в Declarative Mode.
- [x] Использовать Material UI, TanStack Query, React Hook Form и Zod.
- [x] Реализовать REST API на NestJS с Express adapter.
- [x] Генерировать OpenAPI через NestJS Swagger.
- [x] Использовать SQLite и Drizzle ORM.
- [ ] Использовать серверные сессии в HttpOnly cookie.
- [x] Использовать Argon2 для хеширования паролей.
- [x] Использовать Pino для структурированных логов.
- [ ] Использовать Vitest, React Testing Library, Supertest и Playwright.
- [x] Не использовать Docker, Redis, внешнее файловое хранилище и фоновые очереди.

Целевая структура:

```text
roomly/
├── apps/
│   ├── web/
│   └── api/
├── packages/
│   └── api-client/
├── data/
├── docs/
├── scripts/
├── .env.example
├── .nvmrc
├── package.json
└── package-lock.json
```

`data/` используется для локальной базы и других runtime-данных и не добавляется в Git. Изображения комнат хранятся в SQLite как BLOB: это упрощает атомарное создание и изменение комнаты и не требует отдельного хранилища.
